# Red team: which detectors fire on honest data

A false-positive rate measured on a control chosen by the person who built the detector is
weak evidence, because they chose a control they expected to pass. This document records the
opposite exercise: for each confound in the four project `known_traps.md` files and in this
library's own `docs/known_traps.md`, data generated by an honest process designed to make a
detector fire, and what each detector actually did.

Everything here is **measured**, not expected. Where a trap failed to break a detector that
was supposed to be fragile, that is recorded as a survival with the numbers, because a
red-team document that only lists successes is a document that has never been able to fail.

The generators are in `forensics_core.redteam`; the pass is reproduced by
`tests/test_redteam.py`. Every generator produces data with **no injected distortion** — that
property is asserted arithmetically, not asserted in prose. This is the counterpart to
`forensics_core.inject`, which puts a distortion in and measures whether the detector finds
it: `inject` measures power, `redteam` measures the false positives that make power readable.

## `gosplan-9` — transcription error mimics everything

> Digit tests on OCR'd tables detect OCR. Only run them on tables whose inter-transcription
> error rate is documented and low. — `projects/gosplan/docs/known_traps.md`, §9

The trap has **two modes and they are not equally dangerous**. This is the finding that
matters most in this document, because a detector that survives the first has not been shown
to survive the second, and the obvious test only exercises the first.

### Uniform misread — SURVIVES

A scanner that misreads a digit as any of the other nine with equal probability. Measured with
`ocr_noise(values, rate, positions=(0,))`, n = 4000, 60 seeds per rate, `terminal_digit_test`
at α = 0.05:

| error rate | fired |
|---|---|
| 0.05 | 6/60 = 0.100 |
| 0.25 | 4/60 = 0.067 |
| 0.50 | 5/60 = 0.083 |
| 1.00 | 5/60 = 0.083 |

Every one of these is inside Monte Carlo error of the nominal 0.05 (SE = 0.028 at 60
replicates). The rate at which every last digit is misread — 1.00 — is no worse than the rate
at which none is. That is not a coincidence and not a robustness result: a uniformly wrong
digit is still a uniformly distributed digit, and a test for uniformity cannot see it.

### Glyph confusion — FIRES

A scanner that resolves several glyphs to one, which is what OCR failure actually looks like.
Measured with `confusion={3: 8, 5: 8, 6: 8, 9: 8}`, otherwise identical:

| error rate | fired |
|---|---|
| 0.02 | 20/60 = 0.333 |
| 0.05 | 54/60 = 0.900 |
| 0.10 | 60/60 = 1.000 |
| 0.15 | 60/60 = 1.000 |
| 0.25 | 60/60 = 1.000 |
| 0.50 | 60/60 = 1.000 |

**A 5% glyph confusion rate makes the terminal-digit test fire nine times in ten on a table
nobody falsified.** At 10% it fires every time. A clean table of the same size and
construction fires 3 of 60.

Note that a 5% *confusion* rate is a smaller corruption than a 5% *misread* rate: only four of
the ten digits are confusable here, so about 2% of last digits actually change. The test is
reacting to the shape of the corruption, not its size.

### Consequence: the OCR gate

`terminal_digit_test` **may not be run on transcribed data** until the transcription disagreement rate has been measured for the
real inter-transcription error rate and shown it below the firing threshold. On the grid
above the threshold is **0.05** (the lowest tested rate at which the test fires in more than
half of replicates).

`redteam.ocr_firing_threshold` computes that number for any detector and
`redteam.ocr_gate(threshold, measured_rate)` answers whether the gate opens. `ocr_gate`
returns `False` when the threshold is `None` — a detector that could not be made to fire on
the grid tested has not been shown safe at an unmeasured rate, and the response is to widen
the grid, not to proceed.

## `elections-1` — small precincts produce round percentages honestly

> A precinct with 100 registered voters can legitimately report exactly 70.0% turnout. Any
> integer-percentage test that does not weight or condition on precinct size detects
> arithmetic, not fraud. — `projects/elections/docs/known_traps.md`, §1

**Verdict: survives, contrary to expectation.**

This trap was expected to be the headline result, and a single draw can be made to show it: at
seed 10, with denominators drawn from {60, 80, 100} and n = 3000, `integer_excess` with
`min_denominator=1` returns p = 0.026 on honest binomial data. It does not replicate.

Measured over 100 replicates, `integer_excess` at α = 0.05, `n_mc=200`:

| denominators | `min_denominator=1` | `min_denominator=100` |
|---|---|---|
| {60, 80, 100} | 8/100 = 0.080 | 0/100 = 0.000 |
| {60, 80} | 3/100 = 0.030 | every unit excluded |
| {100} | 0/100 = 0.000 | 0/100 = 0.000 |
| {50, 100, 150} | 8/100 = 0.080 | 7/100 = 0.070 |
| {20, 50, 100} | 0/100 = 0.000 | 0/100 = 0.000 |

Monte Carlo SE at 100 replicates is 0.022, so 0.080 sits 1.4 SE above nominal. Under
`control.classify` that is `calibrated`, not `anticonservative`. **There is no finding here.**

The reason is in the estimator and is worth stating, because it is the mitigation working
rather than the trap being unreal. The Kobak–Shpilkin–Pshenichnikov null redraws each
numerator as `Binomial(denominator, p)` *at that precinct's own denominator*, so the integer
mass a small precinct produces honestly appears in the null distribution as well as in the
observed data and cancels. The pure case is the {100} row: with a denominator of exactly 100
every possible percentage is an integer, observed and null both equal 3000, the null SD is 0,
and p = 1.0.

`min_denominator` is therefore a second line of defence rather than the mechanism that makes
the test safe. On the {50, 100, 150} row it removes almost nothing (0.080 → 0.070).

**What this does not establish.** These are synthetic denominators drawn from small fixed
pools at a constant rate `p`. Real precinct files have a continuous size distribution,
size-correlated turnout, and regional structure. The trap remains a live concern for a real
file and `min_denominator` should stay set; what has been ruled out is the specific failure of
the binomial null failing to absorb denominator-driven integer mass.

### A refusal is not a survival

With denominators of {60, 80} and `min_denominator=100`, every unit is excluded and
`integer_excess` raises. `red_team` records that as an error with `pvalue=None`, not as a
non-firing. A report that scored a refusal to answer as a clean bill of health would be
reading silence as evidence.

## `core-1` — honest series are persistent

> Output levels, shares, rates and growth rates carry over from one period to the next. A
> stationary series is not an exchangeable one. — `docs/known_traps.md` (this repository), §1

**Verdict: `too_smooth_test` FIRES under every `detrend` option, each on its own shape.**

`persistent_series(n, rho, kind=...)` draws a stationary AR(1) with iid normal shocks, started
from its stationary distribution. `kind="levels"` returns the level (mean 0, shock sd 1);
`kind="growth"` returns a log level that cumulates an AR(1) growth rate (mean 0.02, shock sd
0.01). Measured with `red_team` at n = 50, seeds 0–99, `too_smooth_test` with `n_perm=199` and
permutation seed 0, α = 0.05:

| shape | rho | `detrend="none"` | `detrend="linear"` | `detrend="diff"` |
|---|---|---|---|---|
| levels | 0.0 | 5/100 | 1/100 | 0/100 |
| levels | 0.3 | 64/100 | 55/100 | 0/100 |
| levels | 0.5 | 95/100 | 89/100 | 0/100 |
| levels | 0.7 | 99/100 | 99/100 | 0/100 |
| growth | 0.0 | 100/100 | 100/100 | 5/100 |
| growth | 0.3 | 100/100 | 100/100 | 61/100 |
| growth | 0.5 | 100/100 | 100/100 | 95/100 |
| growth | 0.7 | 100/100 | 100/100 | 99/100 |

At rho = 0 the `none` and `linear` levels rows, 5/100 and 1/100, are 0 and 1.8 Monte Carlo
SE from nominal (SE 0.022 at 100 replicates), so what fires above them is the persistence, not
a broken test. `diff`'s 0/100 there is 2.3 SE below nominal and is not calibration: on levels
`diff` has no power, for the reason given below. A modest persistence of 0.3 is enough to make
`none` and `linear` fire on more than half of honest series. The growth rows at rho = 0 are a
random walk with drift, which `none` flags as a trend (its docstring says so) and whose
`linear` residuals are themselves persistent.

**`diff` is not a safe harbour.** Its 0/100 on persistent levels is lack of power rather than
robustness: on iid levels its mean p is 0.998 (the docstring's calibration). On a persistent
growth rate it fires like the other two.

**The power atlas could not see this.** `power_curve`'s default sampler returns units in
random order. On an honest AR(0.7) population of 20,000 (`persistent_series(20000, 0.7,
seed=2028)`, lag-1 autocorrelation 0.697), `too_smooth_test(detrend="none")` with
`inject_smoothing` as the injector and 100 replicates:

| sampler | false-positive row at n = 50 / 100 / 300 | `minimum_detectable_effect` at 300 |
|---|---|---|
| `sampling="units"` | 0.04 / 0.04 / 0.02 | 0.5, calibration check passed |
| `sampling="contiguous"` | 1.00 / 1.00 / 1.00 | refused: false-positive rate 1.000 |

Cut into its 66 contiguous windows of 300, the same series is rejected in 66 of 66. The
`units` row is the test on exchangeable data, whatever population was supplied; the
`contiguous` row is the test on the series. An order-dependent test belongs in the atlas only
with `sampling="contiguous"` and a population at least as persistent as the honest data.

**Consequence.** A `too_smooth_test` rejection on a time series says the analysed values are
not exchangeable, and nothing more until the same test has been shown not to fire on an honest
series as persistent as the one tested. The registered `too_smooth` detector defaults to
`diff`, so on persistent levels it does not fire; what it costs there is power.

## Traps generated but not yet run against a detector

These generators exist and their honesty is asserted, but no detector in `forensics_core`
currently consumes their output in a form this pass can score. They are listed so that the
gap is visible rather than absent.

| trap | generator | why not yet scored |
|---|---|---|
| `elections-2` honest bimodality | `heterogeneous_mixture` | The turnout-bimodality analysis is a project-level module that still raises `NotImplementedError` (CONTRACT rule 4). Scoring it belongs to that project. |
| `china-2` boundary changes | `level_shift` | `dispersion.too_smooth_test` operates on per-unit collections; a break test is not yet a registered detector. |
| `gosplan-3` index-number problem | `reweighting` | Same: no detector currently takes a growth index as input. |

Each of these is a real trap from a real document, and leaving them unscored is a stated
limitation of this pass, not a claim that the detectors survive them.

## Reproducing

```
uv run pytest -q tests/test_redteam.py
```

The 60- and 100-replicate figures above, and the 66-window count, are measurements run once
and recorded here; the test suite re-checks them at a smaller budget sufficient to catch a
gross regression, and each such test names the number in this document that it is guarding.
The atlas rows for `core-1` are re-checked in `tests/test_power_atlas.py`. If a test here
starts failing, the document is what must be updated — not the assertion.
